# Validation record

Run date: 2026-11-16. This is an implementation/coverage record, not a HEIF or HEVC conformance certificate.

## Uncompressed HEIF image items (`unci`, 2026-11-16)

ISO/IEC 23001-17 defines uncompressed 2D images in ISO base media files; this is a generic HEIF image path, not HEVC-coded HEIC decoding. The implementation accepts version-0 custom `uncC` configurations with essential `uncC` and `cmpd` properties, unsigned components at independent 8–16-bit depths, signed two's-complement components at independent 2–16-bit depths, IEEE 754 float components at 16/32/64/128/256-bit widths, and complex components at 32/64/128/256 total bits (two IEEE floats at half-width each). `decodeHeicUncompressedComponents` exposes raw component planes; complex values are alternating real/imaginary numbers in `Float64Array`, signed integers are sign-extended, and source float values are not normalized. Binary128 values are converted to JavaScript numbers and therefore do not retain all binary128 precision. Signed values are mapped to display code values with zero at the midpoint; this is the renderer's interpretation of signed image samples. The version-0 predefined `rgb3` configuration (packed 8-bit R, G, B) and version-1 `yv20` profile (implicit or matching `cmpd` component order Y, V, U, 8-bit planar 4:2:0) are also supported. Monochrome, RGB, 4:4:4, 4:2:2, 4:2:0, and 4:1:1 YCbCr are rendered; RGB channels are normalized to their highest declared component depth, while YCbCr retains the luma depth and normalizes Cb/Cr to their higher declared depth. Float components use a 16-bit normalized working range; linear float values remain extended in `decodeHDR`, while SDR output clips to its 8-bit range. The RGBA/HDR rendering path rejects NaN and infinity, as well as finite float samples whose normalized values exceed the Float32 working range; raw component extraction preserves IEEE NaN/infinity values as JavaScript numbers. Inline alpha may use its own supported 2–16-bit signed or 8–16-bit unsigned depth, or a supported float width. Full-resolution components support component, pixel, row, or tile-component interleave; pixel interleave can use `pixel_size` to pad every pixel to its configured byte extent. Subsampled YCbCr supports component or mixed interleave; 4:2:2 and 4:1:1 also support Multi-Y interleave, with Cb/Cr order preserved and chroma plane sizes/rendering selected from the signalled sampling mode. `component_align_size = 0` values are read from the packed MSB-first bitstream; aligned component words support the standard's big-endian and little-endian representations, low-order sample bits, and the full 8-bit field size (up to 255 bytes). Little-endian words require every component to be byte-aligned and `block_little_endian` to be zero. Component-, pixel-, row-, mixed-, and tile-component-interleaved rows are byte-aligned, with optional `row_align_size` padding; under Amendment 2, component-interleaved subsampled chroma uses the configured alignment size without the base-edition divisor, while mixed-interleaved U/V rows are aligned as a pixel-interleaved pair. Component-, pixel-, row-, and mixed-interleaved tile grids use raster tile order; tile-component interleave uses component-major raster tile order. `tile_align_size` is applied at each component or U/V-pair tile-data boundary using the configured value; 4:2:2 requires a multiple of 2, while 4:2:0 and 4:1:1 require a multiple of 4. ISO/IEC 23001-17:2024/Amd 2:2025 replaces the base-edition chroma row/tile alignment divisors and updates the row-size grouping rules. Subsampled tile dimensions are checked against the sampling factors. When present, `pixi` channel counts, component depths, and component formats are checked against `uncC`; metadata reports the configured visual `uncC` depth even when `pixi` is present. Samples use the shared HEIF color and transform rendering path. [ISO/IEC 23001-17:2024](https://www.iso.org/standard/82528.html) · [ISO/IEC 23001-17:2024/Amd 2:2025](https://www.iso.org/standard/89120.html)

Block-pixel interleave is supported for full-resolution components; block-component interleave also supports 4:2:2, 4:2:0, and 4:1:1 YCbCr, as these sampling modes permit component interleave. Both layouts support unsigned 8–16-bit, signed 2–16-bit, and IEEE 754 float (16/32/64/128/256-bit) components, with component and pixel blocks up to 255 bytes. The decoder handles block endianness, block padding placement, pixel component reversal, and row/tile alignment; block mode cannot be combined with component alignment or `components_little_endian`. The pixel-block size is capped at 255 bytes to bound per-pixel BigInt work, although its field is wider. The latest `pixi` extension accepts component format 3 for signed channels and cross-checks it against signed `uncC` components; HEVC-coded image samples remain unsigned-only. The RGBA renderer rejects complex components because the format defines no standard RGBA mapping; raw extraction is capped at 256 MiB of output component data. Generic compression handles `defl` raw DEFLATE, `zlib`, and `brot` Brotli through essential `cmpC` properties; `icef` compressed-unit ranges are validated and decompressed in order, with output capped at 256 MiB per item and async decoding capping the prepared total at 512 MiB. Sync decompression uses Node.js zlib; async decoding uses `DecompressionStream` when the runtime supports the requested format, with Node.js fallback. Synthetic tests compare whole-item compressed results and independently compressed tile results with their uncompressed pixels through synchronous SDR, async SDR, and synchronous HDR APIs; malformed compressed data and out-of-range `icef` ranges are rejected. `test/uncompressed-image.test.ts` compares the version-0 `rgb3` result with the equivalent custom RGB configuration and rejects a mismatched component order; it also checks version-1 `yv20` decoding against the equivalent explicit version-0 configuration, including omitted and matching `cmpd`, and rejects mismatched component order. Synthetic float tests cover all five component widths through synchronous and asynchronous RGB/HDR/SDR conversion, matching per-channel `pixi` metadata at 16/32/64/128-bit depths, component-interleaved YCbCr, both aligned word byte orders, all float widths in block-pixel, block-component, row-interleaved, and tile-component-interleaved layouts, monochrome with inline alpha, negative finite values, NaN and infinity rejection, Float32-range rejection, and extended linear HDR values. `decodeHeicUncompressedComponents` is tested through the package entry point with complex 32/64-bit components, finite and non-finite IEEE values, aligned little-endian words, block-pixel packing, Multi-Y phases, and sign-extended signed integers; ordinary RGBA decoding rejects the complex-only fixture. No official ISO reconstruction vector for complex components was located. Other synthetic payloads cover block-packed component-interleaved 4:2:2, 4:2:0, and 4:1:1 YCbCr, signed 2-bit/3-bit/8-bit/10-bit samples, including one-byte alignment, aligned little-/big-endian words, block layout, signed RGB and YCbCr rendering, and signed per-channel `pixi`, plus pixel-interleaved RGBA with per-pixel `pixel_size` padding (including 10-bit aligned RGB), component-interleaved RGB, packed 10-bit component rows with and without configured row alignment, pixel- and row-interleaved rows, row-interleaved tiled RGB with row and tile alignment, mixed-interleaved 4:2:0 row alignment, component-interleaved subsampled rows using the Amendment 2 alignment size, 10-bit aligned RGB/RGBA/YCbCr (including 4-byte and 255-byte component words, with and without matching `pixi`), 10-bit RGB with 8-bit alpha, mixed 8/10/12-bit RGB, 12/8/10-bit Y/Cb/Cr, mixed packed/aligned words, mixed-interleaved 4:2:0 with reversed Cb/Cr declaration order, Multi-Y 4:2:2 and 4:1:1 component groups with inline alpha, mixed component depths, pixel_size padding, tile alignment, and invalid group-size rejection, component/pixel/mixed tile grids with row and tile alignment, component and mixed 4:2:2/4:2:0 tile grids using the configured `tile_align_size` at each component or U/V-pair boundary, component-major tile-component grids with per-component tile alignment, tiled 4:2:2 chroma planes, and 4:4:4/4:2:0/4:1:1 YCbCr, plus metadata-conflict, invalid-layout, and missing-required-property rejection. No official ISO/IEC 23001-17 reconstruction vector for float or complex `unci`, signed `unci` samples, or block layouts was located. Amendment 2:2025 also adds signed sample components. [ISO/IEC 23001-17:2024/Amd 2:2025](https://www.iso.org/standard/89120.html)

## HEIF required reference types (`rref`, 2026-11-15)

ISO/IEC 23008-12 defines `rref` as an essential property naming the item-reference types a reader must process for the associated image. Predictively coded images have the narrower normative rule: their required type is exactly `pred`. For non-predictive items, the parser now accepts required `auxl`, `dimg`, `exbl`, `prem`, and `tbas` references that its auxiliary, derived-image, layered-image, alpha, and relative-location paths process; a declared relation must exist. Unknown required types remain unsupported. [ISO/IEC 23008-12:2025](https://www.iso.org/standard/89035.html)

`test/heif-rref.test.ts` checks required `dimg`, `auxl`/`prem`, and `tbas` paths, missing and unknown relations, and the pred-only constraint with synthetic HEIF wrappers. `test/lhevc.test.ts` checks a required `exbl` declaration with a synthetic L-HEVC configuration. `bun run validate:hevc-exbl` wraps the official `HYBRID_A_QUALCOMM_1` POC 0 access unit in a synthetic HEIF file whose `lhv1` item declares essential `rref(exbl)` and references an `hvc1` base item. The base item matches the official base-frame Y/Cb/Cr samples, and the enhancement item matches all three official OPL plane hashes. This validates the combined required-reference and external-base path, but no official `rref` property reconstruction vector was found.

## HEIF colour information property forms (`colr`, 2026-11-14)

ISO/IEC 23008-12 §6.5.5 permits colour information properties by `colour_type`; CICP `nclx` and ICC profile forms serve distinct purposes, and their association order is not semantically significant. The parser now collects `nclx`, `prof`, and `rICC` independently, rejects duplicate instances of the same type, and returns all ICC forms through `getHeicMetadata().iccProfiles`. For the existing single-profile rendering path, `prof` is selected ahead of `rICC` when both are present; the full list remains available to callers. [ISO/IEC 23008-12:2025](https://www.iso.org/standard/89035.html)

`test/heif-colr.test.ts` attaches synthetic `nclx`, `prof`, and `rICC` properties to the official 10-bit 4:2:2 PCM HEVC item, checks order-independent metadata and deterministic profile selection, and rejects duplicate or truncated declarations. The HEVC payload is official; the property combinations are synthetic, and no official dual-profile reconstruction vector was found.

## HEIF camera calibration properties (`cmex`/`cmin`, 2026-11-14)

The parser returns every `cmex` camera-pose property and the single permitted `cmin` intrinsic property when they precede image transforms. Multiple `cmex` properties must each signal a world-coordinate-system ID. Version-0 `cmex` position and quaternion components and version-1 position plus yaw/pitch/roll rotation angles are decoded; unknown later versions retain their raw property payload. `cmin` version 0 supports simplified and full intrinsics, including the two flag-derived denominators. Its pixel-valued matrix uses the output dimensions after `clap`, `iscl`, and `irot` transforms. Descriptive camera properties after the first transform property are ignored as required by Amendment 1. The metadata does not alter decoded pixels. [ISO/IEC 23008-12:2025](https://www.iso.org/standard/89035.html) · [ISO/IEC 23008-12:2025/Amd 1:2025](https://www.iso.org/standard/89044.html) · [ISO/IEC 23090-7:2022](https://www.iso.org/standard/78989.html)

`test/heif-camera.test.ts` uses synthetic camera-property wrappers around Nokia's official 10-bit 4:2:2 PCM HEVC item. It checks multiple extrinsics and required IDs, signed coordinates, version-0 quaternion fields, version-1 rotation angles, both intrinsic forms, transformed matrix dimensions, ignored post-transform metadata, unknown-version raw preservation, malformed fields, and unchanged decoded pixels. The HEVC payload is official; camera properties and wrapper ordering are synthetic, and no official camera-calibration reconstruction vector was found.

## HEVC active parameter-set selection (2026-11-14)

An HEVC slice selects a PPS by `slice_pic_parameter_set_id`, and that PPS selects an SPS by `pps_seq_parameter_set_id`; an `hvcC` record can carry multiple parameter-set NAL units. The decoder now resolves that active pair for metadata, pixel decoding, and grid/`tili` tile sizing instead of assuming the first SPS/PPS array entry is active. Missing or conflicting IDs are rejected. This follows the parameter-set references defined by [ITU-T H.265 V11](https://www.itu.int/rec/T-REC-H.265-202601-I/en) and HEVC carriage in [ISO/IEC 14496-15:2024](https://www.iso.org/standard/89118.html?browse=tc).

`test/hevc-picture.test.ts` adds a synthetic HEIF item whose `hvcC` contains a 96×64 decoy SPS first, while its slice/PPS select a 64×64 SPS second. Metadata resolves 64×64, and both SDR and HDR outputs match the original item byte-for-byte. The wrapper and multi-SPS arrangement are synthetic; this is not a published multi-SPS HEIF conformance vector. Existing grid and `tili` tests cover the tile rendering paths affected by active SPS sizing.

## HEVC reserved SPS/PPS extension data (2026-11-14)

H.265 V11 clauses 7.4.3.2.1 and 7.4.3.3.1 require decoders to allow nonzero reserved SPS/PPS extension bits and ignore the associated `sps_extension_data_flag` / `pps_extension_data_flag` syntax. Writers conforming to this edition still signal zero; accepting nonzero values is a decoder forward-compatibility requirement. The SPS and PPS parsers now retain alignment through their defined extension fields, accept nonzero reserved bits, and ignore following extension data. Defined 3D extension syntax remains unsupported.

`test/hevc-layered-sps.test.ts` and `test/hevc-layered-pps.test.ts` construct synthetic base/enhancement SPS and PPS NAL units with nonzero reserved bits and varied extension-data flags. These test the normative decoder behavior; no official conformance vector can carry nonzero reserved values because conforming bitstreams must signal zero. Existing official-vector decoder tests remain the sample regression coverage. [ITU-T H.265 V11](https://www.itu.int/rec/T-REC-H.265-202601-I/en)

## HEIF relative location (`rloc`, 2026-11-14)

The optional `rloc` full property exposes its unsigned horizontal and vertical pixel offsets plus the one related image item identified by `tbas`. Since the standard requires `rloc` when `tbas` is present and identifies the related item through that reference, missing properties, duplicate properties, malformed headers, self-links, and missing or ambiguous targets are rejected. `test/heif-rloc.test.ts` attaches synthetic `rloc`/`tbas` metadata to an official 10-bit 4:2:2 PCM HEVC payload and checks the returned offsets and related item ID, including invalid relationship cases. ## HEVC auxiliary image sample planes (2026-11-14)

HEIF identifies auxiliary image items through `auxC` and `auxl`. ISO/IEC 23008-12 specifies that an HEVC-coded auxiliary image uses an `hvc1` or `lhv1` item and that its `auxC` subtype may carry length-prefixed SEI NAL units. `decodeHeicAuxiliaryPlanes()` decodes associated HEVC items and returns Y/Cb/Cr arrays at their original sample depth, with the HEVC conformance window applied. It also returns each item's color, pixel-spacing, and transform metadata; container transforms are not applied to these raw planes. The API parses H.274 depth-representation (payload type 177) and alpha-channel (payload type 165) SEIs from that subtype, retaining the coded values and message order. `interpretHevcDepthSample()` implements all four defined DRI sample interpretations, including the piecewise-linear type-3 disparity LUT. When both finite endpoints are signalled, it also derives a disparity or Z value using those endpoints; H.274 leaves Z units unspecified. This sample conversion does not perform view synthesis. Final SDR and HDR compositing applies valid ACI transparent/opaque values, clip/increment flags, and the premultiplied-black indication; it leaves the raw auxiliary-plane API untouched. [ISO/IEC 23008-12:2025](https://www.iso.org/standard/89035.html) · [ITU-T H.274 V4 (01/2026), §§8.22–8.23](https://www.itu.int/rec/T-REC-H.274-202601-I/en)

`test/auxiliary-images.test.ts` wraps the official 10-bit 4:2:2 `IPCM_A_RExt_NEC_2` HEVC item as a synthetic `auxl` depth image. All three returned component planes match the archived FFmpeg sample reference byte-for-byte. Synthetic `auxC` subtype cases exercise a type-3 depth-representation message with all four optional values and nonlinear models, reserved depth types, 10-bit alpha metadata, message cancellation, and malformed subtype rejection. A synthetic 8-bit monochrome alpha item checks ACI inversion through SDR and HDR composition while confirming that `decodeHeicAuxiliaryPlanes()` still returns the original samples. `test/hevc-tili.test.ts` checks ACI composition on external monochrome alpha tiles. The coded HEVC inputs are fixture vectors; the ACI values and HEIF auxiliary relationships are synthetic. No official decoded depth-map or auxiliary-SEI conformance vector was available in the checked fixture set.

`test/hevc-depth.test.ts` checks normalized type-0 inverse-Z, type-1 disparity, type-2 Z, and type-3 nonlinear disparity mapping against H.274 V4 equations, including signalled endpoints and the reserved exponent used for unspecified values. These are synthetic SEI parameter cases: the checked fixture set does not contain an official depth-representation SEI sample.

## HEIF image scaling (`iscl`, 2026-11-14)

The `iscl` full property now parses its four nonzero 16-bit ratio fields, preserves property-association order relative to crop/rotation/mirror operations, and scales rendered SDR or linear-HDR RGBA. Each output dimension uses the standard ceiling of the input dimension multiplied by its ratio. Scaled output goes through the existing `maxPixels` and derived-image work limits. `applyTransforms: false` leaves the image before container scaling. The HEIF specification defines dimensions and ratios but leaves sample reconstruction filtering to the implementation; this decoder uses center-aligned bilinear interpolation. [ISO/IEC 23008-12:2025, 6.5.13](https://www.iso.org/standard/89035.html)

`test/heif-iscl.test.ts` wraps the official 10-bit 4:2:2 PCM HEVC payload with synthetic `iscl` properties and checks ceiling dimensions, property order with rotation, the untransformed output, malformed fields, and the scaled-output resource limit. The HEVC payload is official, but the HEIF scaling properties are synthetic; no official `iscl` reconstruction vector was found. Resized pixel values are not compared to a reference because the property does not prescribe a reconstruction filter.

## Per-channel HEIF pixel information (ISO amendment 2, 2026-11-14)

ISO/IEC 23008-12:2025/Amd 2:2026 extends the `pixi` property with optional per-channel identifiers, component formats, subsampling information, and UTF-8 labels. `parsePixi` reads the `px_flags` extension and validates its reserved values, field bounds, channel labels, and the single-alpha-channel constraint. `bun test test/pixi.test.ts` checks the legacy form, the amendment's extended syntax, malformed and reserved values, channel-identity-based depth checks, chroma-format consistency, and an official 10-bit 4:2:2 PCM HEVC vector rewrapped with synthetic extended `pixi` metadata. ## HEVC 4:2:0 SPS chroma sample location (2026-11-14)

`parseSps` retains the VUI top- and bottom-field chroma location codes, checks their H.274 V4 range of 0–6, and exposes one render location only when both agree and the value identifies a known sample position. Code 6 is valid and means the location is unknown or unspecified, so it does not select an upsampling phase. The renderer uses a known SPS location as a fallback for 4:2:0 chroma upsampling; explicit container locations take precedence. H.265 defines these VUI locations for `chroma_format_idc = 1` and says to ignore them for other chroma formats. The focused SPS test checks known, differing, unknown, ignored-format, and out-of-range values. [ITU-T H.274 V4, VUI chroma-location semantics](https://www.itu.int/rec/dologin_pub.asp?id=T-REC-H.274-202601-I%21%21PDF-E&lang=e&type=items), [ITU-T H.265 V11](https://www.itu.int/rec/T-REC-H.265-202601-I/en)

The synthetic SPS parser check covers two shared locations, unequal field locations, ignored 4:2:2 values, and an out-of-range code. The `pixi` render check uses the official PCM code stream with a synthetic container wrapper. No official sample-location RGB reference vector was found, so these checks validate parser mapping and the effect of the selected reconstruction location, not normative RGB conformance.

## HEVC SPS VUI default display window (2026-11-14)

`parseSps` retains the four `default_display_window` offsets and validates that their combined region with the conformance crop remains inside the coded picture. The offsets use the HEVC `SubWidthC`/`SubHeightC` units and are available as `getHeicMetadata().sps.defaultDisplayWindow`. H.265 defines this as the suggested display area when no alternative display indication is present. The public `applyDefaultDisplayWindow` option applies it after the mandatory conformance crop for a single coded HEVC item; a container `clap` takes precedence. Grid and `tili` geometry remains container-controlled. The option defaults off because the VUI value is a display hint. [ITU-T H.265 V11](https://www.itu.int/rec/T-REC-H.265-202601-I/en)

The synthetic SPS tests check parsing, absent-flag behavior, range rejection, and 4:2:0/4:2:2 crop-unit mapping on known sample planes. One public-decoder regression requests the option on the unmodified official `CONFWIN_A_Sony_1` vector and confirms its 416×240 coded / 412×236 conformance-cropped output remains sample-identical. A separate end-to-end test uses that vector's first access unit and inserts a synthetic `[1, 1, 1, 1]` VUI default window into its SPS while leaving the coded picture untouched. With the option off, pixels remain identical to the original; with it on, the 4:2:0 display output is 408×232 and sample-identical to a two-pixel inset of the unmodified render. This validates the render path against official coded samples, but is not an official non-zero-window vector. The official HEVC_v1 directory has no test named for this VUI field; a corpus-wide scan of every archive's SPS was not performed.

## Low-overhead HEVC, AVC, and uncompressed still images (`mif3`/`mini`, 2026-11-16)

ISO/IEC 23008-12:2025/Amd 2:2026 adds the low-overhead image-file structure: a `mif3` structural brand and a `mini` MinimizedImageBox that represents the regular MetaBox/MediaDataBox form. The decoder reads version-0 HEVC `mini` items directly, including codec configuration, dimensions, HEIF-representable integer bit depths (8–15), CICP defaults or explicit values, all eight orientation values, and one optional HEVC alpha item with its own codec configuration. It interprets chroma-centering bits and bilinearly upsamples at the signalled sample positions. ICC bytes are retained in `HeicInfo.icc`; Exif/XMP bytes are exposed through `HeicInfo.miniMetadata`, along with their shared compressed-payload flag. Integer gain-map HDR is normalized to the existing ISO `tmap`/gain-map reconstruction path, including the gain-map dimensions, item, metadata, tone-mapped CICP/ICC, and optional HDR-property blocks.

The `mif3` structural brand may appear as the major brand or a compatible brand. The decoder also accepts a nonzero `minor_version` that names the brand of the equivalent regular file, when the mini header explicitly carries the codec types. Synthetic YV20 mini wrappers exercise both brand arrangements and compare their decoded RGBA output with the major-`mif3` equivalent. The ISO conformance fixture below covers the major-`mif3` case; no official end-to-end vector for compatible-brand or expanded-brand `minor_version` signaling was located. [ISO/IEC 23008-12:2025/Amd 2:2026](https://www.iso.org/standard/90273.html) · [MPEG DAM 2 text and meeting documents](https://www.mpeg.org/standards/MPEG-H/12/)

When the mini header explicitly identifies its item codec, the generic `mif3` form can also carry an uncompressed `unci` image. The integer version-1 `yv20` configuration (8-bit planar Y, V, U 4:2:0) is parsed inline without a separate `cmpd`, then rendered through the regular uncompressed-image path. A synthetic 2×2 mini wrapper matches the same payload in a regular HEIF `unci` file sample-for-sample after matching CICP and range signaling. ## Tone-map version fallback

ISO/IEC 23008-12:2025 Amendment 1 defines `ToneMapImage.version` as 0. ISO 21496-1:2025 defines `minimum_version` as 0 for its first edition and requires `writer_version >= minimum_version`. A reader that encounters a ToneMapImage version it does not understand, or a gain-map metadata minimum version it does not support, ignores the tone-map metadata and uses the base image. The SDR decoder already resolves `tmap` to its base image. The HDR decoder now follows the same fallback: it returns the base image linearized according to its own color metadata, without applying the gain map. With `minimum_version = 0`, the parser also ignores trailing padding or optional extension bytes after the known fields, as permitted by ISO 21496-1 Annex C.2.1. [ISO/IEC 23008-12:2025/Amd 1](https://www.iso.org/standard/89044.html) · [ISO 21496-1:2025](https://www.iso.org/standard/86775.html)

A `mini` case uses Nokia's official C71 HEVC item as its base and confirms the same fallback for an unsupported gain-map minimum version. ## ICC RGB and monochrome color management (2026-11-14)

SDR decoding applies ICC RGB input/display profiles that use the matrix/TRC model and XYZ PCS: channel tone curves linearize encoded RGB values, the colorant matrix maps them to XYZ, and the result is adapted to D65 linear sRGB and encoded as sRGB. Monochrome input/display profiles use `kTRC` and the achromatic PCS axis. For XYZ PCS, its D50 white is converted to linear sRGB; for Lab PCS, normalized `grayTRC` output supplies L* while a* and b* are zero. The required `wtpt` tag is validated, while relative-colorimetric gray conversion follows Annex F.2's PCS-white formula. RGB and monochrome scanner/display profiles may provide `A2B0`/`A2B1`/`A2B2` transforms encoded as `mAB`, `mft1` (`lut8Type`), or `mft2` (`lut16Type`), and `D2B0`/`D2B1`/`D2B2`/`D2B3` MPE transforms; the `mAB`, `mft2`, and supported MPE paths also support XYZ PCS. The `iccRenderingIntent` option selects `A2B1` for relative (default), `A2B0` for perceptual, `A2B2` for saturation, or `D2B3` for absolute. Absolute intent uses `D2B3` directly when available; otherwise, supported relative transforms are converted using the profile media white point before the existing `A2B0` and matrix/TRC fallbacks. The `mAB` path applies A curves, one- or three-dimensional CLUT interpolation, M curves, a 3×4 matrix, and B curves. The legacy `mft1`/`mft2` path applies the identity matrix, one- or three-dimensional CLUT interpolation with the first input dimension varying slowest, and the ICC-defined input/output tables. Lab output is converted from the legacy 8- or 16-bit Lab PCS encoding to D50 Lab. XYZ output follows the ICC 16-bit PCSXYZ `u1Fixed15` scale (`0x8000` = 1.0), then converts D50 XYZ to linear sRGB. Since ICC does not define an 8-bit PCSXYZ encoding, `mft1` with XYZ PCS is rejected as implementation-specific. `mft1` uses 256 entries per table; `mft2` accepts 2–4,096 entries. Supported LUT transforms have three output channels and one (GRAY) or three (RGB) input channels. Profiles with only `A2B1` and neither `A2B0` nor a complete matrix/TRC fallback remain unsupported unless an intent-matched `D2B` MPE transform is available. HEIF `prof` accepts these LUT profiles; restricted `rICC` rejects all LUT transforms. [ICC.1:2022](https://www.color.org/specifications/ICC.1-2022-05.pdf) Annex F.2/F.3 and the [ICC profile embedding note](https://archive.color.org/files/technotes/ICC-Technote-ProfileEmbedding.pdf) define the profile models and HEIF restrictions. The ordinary `decode` path routes profiled images through these conversions.

ICC.1:2022 §10.16.2.4 defines the MPE CLUT as p-dimensional, where p is the element input-channel count, and its encoding reserves 16 entries for per-dimension grid counts. ## ISO HEIF tiled image item (`tili`, 2026-11-12)

## Fractional HEIF clean aperture (2026-11-10)

ISO/IEC 23008-12 defines `clap` as a cropping transform and reuses the rational clean-aperture geometry from ISO/IEC 14496-12. Apple’s QuickTime file-format documentation also describes fractional aperture dimensions and offsets. Since this decoder returns an integer pixel raster, non-integral geometry is rendered with output dimensions rounded to the nearest integer (minimum one pixel) and bilinear interpolation between the aperture’s endpoint sample centers; a one-pixel output samples the aperture center. Integral geometry keeps the exact-copy crop path. The raster filter and integer sizing are implementation choices, not a claim of matching a normative sample-exact vector.

The synthetic regression uses a 31.5×15.5 aperture with horizontal offset `1/4` and vertical offset `−1/4`, then rotates the 32×16 raster. It compares every output channel against an independently constructed interpolation from the untransformed decoded image. ## Dependent HEVC slice segments (2026-11-10)

H.265 V11 clause 7.4.7.1 says omitted dependent-segment header values are inherited from the preceding independent slice header. Clauses 9.3.1 and 9.3.2.1 require CABAC context/Rice state to be saved at a dependent segment boundary and restored at the next segment; WPP synchronization takes precedence at a row start. Quantization prediction continues within the same slice under clause 8.6.1. The decoder now carries the independent header and slice identity across dependent segments, restores the CABAC state at segment boundaries, and applies WPP row synchronization when enabled.

## HEVC implicit intra RDPCM (2026-11-10)

The SPS parser now exposes `implicit_rdpcm_enabled_flag`. ## L-HEVC item selection metadata (2026-11-11)

### Annex F VPS VUI parsing (2026-11-12)

The VPS parser now reads the syntax between its representation-format table and RBSP trailing bits: active-reference and POC flags, per-OLS DPB sizes, direct-dependency types, optional non-VUI extension bytes, and the VPS VUI. It exposes cross-layer alignment, bit/picture rates, indexed video-signal records, per-layer tile and WPP flags, inter-layer restriction presence, and whether VPS VUI bitstream-partition HRD syntax is present. It reads the video-signal records whether or not the per-layer index flag is set, deriving the table size and layer indices when omitted. Rendering selects the indexed video-signal record for the active output layer and applies the Annex F.15.3.1 inference rule to eligible non-base layers: dependent layers use the VPS values, as does a multilayer-extension SPS with VUI when that layer has no direct reference. Specified HEIF CICP color remains higher priority, and alternative-transfer SEI retains its existing position ahead of SPS/VPS transfer values.

The official ITU-T H.265.1 SHVC vectors `VUI_A_QUALCOMM_1`, `VUI_B_QUALCOMM_1`, and `VUI_C_QUALCOMM_1` are parser checks: A signals VPS VUI, B includes tile information, and C includes per-layer wavefront information. `bun run validate:hevc-vps-vui` verifies pinned archive and bitstream SHA-256 hashes, parses each VPS through VUI and RBSP trailing bits, and asserts the tile or WPP branch in the corresponding vector. Synthetic tests check indexed and inferred video-signal records, per-layer selection, both Annex F.15.3.1 inference conditions, SPS/container/SEI precedence, and fallback behavior. For an external base layer with no signalled video-signal indices, a synthetic VPS also verifies dense mapping of the enhancement-layer records. H.265 V11's prose says the inferred index equals the VPS layer index while also bounding it by the table length; when the base is external those statements disagree for the final layer. ### Annex F PPS colour mapping and Annex H reconstruction (2026-11-12)

### Annex F reference-region offsets and Annex H spatial resampling (2026-11-12)

The PPS parser retains the per-reference `scaled_ref_layer_*_offset`, `ref_region_*_offset`, and resampling phases. The sample path derives reference/scaled regions and the 16.16 spatial scale factors from coded picture sizes and chroma subsampling, maps each output sample to 1/16-sample coordinates, then applies the normative 16-phase 8-tap luma and 4-tap chroma filters with edge clipping and bit-depth promotion. For reference-layer motion, it maps each current 16×16 block centre to the rounded reference-layer 16×16 motion/mode entry and applies the Annex H horizontal and vertical motion-vector scale factors. The motion map distinguishes external inter prediction from SCC IBC so IBC blocks are not misreported as external inter motion.

H.265 V11 clause H.8.1.4.1 requires the scaled **luma** reference-region width and height to be greater than or equal to the corresponding reference-region extent. A smaller luma extent is therefore a non-conforming bitstream, not a supported-feature gap; the decoder reports it as `INVALID_BITSTREAM`. The Annex H process also allows different chroma subsampling between layers, so chroma planes can have fewer output samples even while the luma reference is upscaled; the resampler supports that component-size conversion.

Monochrome/color layer pairs are also rejected as `INVALID_BITSTREAM`. H.265 V11 clause H.11.1.1 restricts Scalable Main and Scalable Main 10 layers to 4:2:0, while H.11.1.2 requires the same `chroma_format_idc` across layers for the scalable format range-extension profiles. ## Reference-tool defect: FFmpeg HEVC QP 74/75

ISO/IEC 23008-12 defines the HEIF storage format and HEVC image brands; it does not define HEVC quantization. This PR is a codec issue: ITU-T H.265 V11 clauses 8.6.1 and 8.6.3 allow the internal inverse-quantization `qP` index to reach 75 for 12-bit components. The coded-domain luma QP is bounded at 51; adding `QpBdOffsetY = 24` yields the internal index used for inverse quantization. The inverse-quantization scale is derived from `levelScale[qP % 6]` and `qP / 6`. Chroma can also reach internal index 75: for 4:2:0, Table 8-10 maps the maximum `qPi` to 51 before adding the bit-depth offset; for 4:2:2 and 4:4:4, clause 8.6.1 applies `Min(qPi, 51)` before that offset. FFmpeg's `rem6` and `div6` arrays allocate 76 entries but initialize only 74, so internal indices 74/75 select a scale of 40 instead of `51 << 12` and `57 << 12`. [ISO/IEC 23008-12:2025](https://www.iso.org/standard/89035.html) · [ITU-T H.265 V11](https://www.itu.int/rec/T-REC-H.265-202601-I/en)

[FFmpeg PR #25467](https://code.ffmpeg.org/FFmpeg/FFmpeg/pulls/25467) fixes those entries and adds two synthetic 12-bit 4:4:4 FATE candidates. The code change is shared by component dequantization, so its correction applies to 4:2:2 streams that reach QP 74/75 too; the attached samples themselves exercise 4:4:4 only. The separate official 12-bit 4:2:2 vector check above does not establish that those exact maximum QP indices occur in that vector. The live API check on 2026-11-15 reports the PR open, unmerged and mergeable at head `ab592e1ed17c49929f3e0ed9c7c833c12b3dbacd`; all 11 distinct status contexts are successful. ## CICP YCbCr matrix coefficients

The renderer uses ITU-T H.273 V4 Table 4 and the corresponding inverse equations for matrix codes 1, 4–15, and 16/17. Code 8 supports equal-depth YCgCo and the `BitDepthC = BitDepthY + 1` YCgCo-R form, including limited-range expansion; other depth pairs are rejected. Codes 16/17 use equations 62–65 for YCgCo-Re/Ro, deriving `BitDepthRGB` as `BitDepthY - 2` or `BitDepthY - 1` and applying full/limited-range scaling at that RGB precision before storing at the renderer's output depth. Limited range is rejected when `BitDepthRGB < 8`, matching H.273's stated range-equation assumption. Codes 12 and 13 derive `KR`/`KB` from H.273 V4 Table 2 primaries 1, 4–12, and 22; unspecified and reserved primary code points are rejected for these matrices. ## HEVC 16-bit conformance versus HEIF configuration

H.265 permits sample arrays with 8–16-bit precision. The official H.265.1 `GENERAL_16b_444_highThroughput_RExt_Sony_2` stream is an elementary-stream conformance vector; its 16 pictures parse as 16-bit 4:4:4. It is not, by itself, a HEIF image item. ISO/IEC 23008-12 Annex B requires an HEVC image item's configuration property to carry the HEVC configuration record. ISO/IEC 14496-15:2024 encodes `bit_depth_luma_minus8` and `bit_depth_chroma_minus8` in three bits each and requires those values to match the activated parameter sets. Consequently, that record can signal depths 8–15, but cannot signal a bit-depth-minus-8 value of 8 (16-bit depth). The 16-bit elementary stream therefore does not establish a missing 16-bit HEIC case; the decoder supports all HEIF-representable integer depths from 8 through 15. The stream was parsed for scope review, not reconstructed. [ITU-T H.265 V11](https://www.itu.int/rec/T-REC-H.265-202601-I/en), [H.265.1 test vectors](https://www.itu.int/rec/T-REC-H.265.1-201810-I/en), [ISO/IEC 23008-12:2025](https://www.iso.org/standard/89035.html), [ISO/IEC 14496-15:2024](https://www.iso.org/standard/89118.html?browse=tc)

## Unequal luma and chroma bit depths

H.265 V11 Annex A constrains luma and chroma depths separately within its format-range profiles; it does not require them to be equal. ISO/IEC 14496-15 carries separate luma and chroma depths in `hvcC`, and HEIF `pixi` can describe those component depths. The decoder now allocates, reconstructs, filters, and renders each plane at its own depth. For `decode`/`decodeHDR`, the existing `bitDepth` remains the luma depth; `bitDepthChroma` is present only when the chroma depth differs.

## HEIF-representable HEVC sample depths

H.265 V11 specifies 8–16-bit luma and chroma sample arrays, independently. The `hvcC` record used by HEIF stores each `bit_depth_*_minus8` value in three bits, so an HEIF HEVC item can signal 8–15 bits; 16-bit HEVC elementary streams cannot be represented by this configuration record.

`bun run validate:hevc-bitdepth-range` starts from the official 416×240 `IPCM_B_RExt_NEC` 12-bit 4:4:4 vector, patches only the SPS component-depth fields, and updates `hvcC`/`pixi` for eight derived images: 8/8, 9/9, 11/11, 13/13, 14/14, 15/15, 9/15 and 15/9-bit luma/chroma. Before using HM as the reference for those derived images, the script verifies that HM's original 12-bit reconstruction matches the checked-in official YUV reference. HM then matches all 299,520 samples in each derived image; synchronous RGBA and HDR results also preserve both component depths. The derived streams are local checks, not separately published H.265.1 vectors. The HM 19.0 reference decoder was built with `HIGH_BITDEPTH=ON`; set `HEVC_HM_DECODER` to that executable when running the script. [ITU-T H.265 V11](https://www.itu.int/rec/T-REC-H.265-202601-I/en), [ISO/IEC 14496-15:2024](https://www.iso.org/standard/89118.html?browse=tc)

## Separate-plane syntax and profile scope

H.265 V11 retains `separate_colour_plane_flag` syntax: when set with 4:4:4, each colour plane is coded with monochrome syntax and decoded independently, with `ChromaArrayType` equal to 0. The current Annex A.3.5 constraints for Format Range Extensions profiles and A.3.6 constraints for High Throughput profiles require this flag to be 0, including their 4:4:4 still-picture profiles. The flag therefore does not identify a valid-format gap for the HEVC profiles this HEIF decoder targets; arbitrary streams that set it while claiming one of those profiles remain rejected. The older H.265 v8 Annex A and JCT-VC HM tracker record the same restriction, but the current-edition rule is decisive.

The official ITU RExt directory contains 49 ZIP vectors (about 73 MB); all embedded bitstreams were scanned and none had the flag set. The ISO/IEC 23008-8 12-bit 4:4:4 vector archive has 14 pictures, also all with the flag clear. No official reconstruction vector for a separate-plane picture was found, so there is no sample-exact conformance result to claim for that syntax. [Current H.265 V11](https://www.itu.int/rec/T-REC-H.265-202601-I/en), [H.265 v8](https://www.itu.int/rec/T-REC-H.265-202108-S/en), [JCT-VC HM ticket #1360](https://hevc.hhi.fraunhofer.de/trac/hevc/ticket/1360), [ITU RExt vectors](https://www.itu.int/wftp3/av-arch/jctvc-site/bitstream_exchange/draft_conformance/RExt/).

## 3D-HEVC extension scope

H.265 Annex I defines 3D texture/depth coding tools, and the SPS/PPS readers currently reject their extension syntax. The official H.265.1 3D Main conformance table tests 30-frame/s streams; its base-layer profile column includes Main but has no Main Still Picture entry. The scanned 3D conformance set therefore establishes video decoding requirements, not a HEIF still-image decoder requirement. This remains outside the current still-image scope; ordinary HEVC auxiliary depth items are handled separately by `decodeHeicAuxiliaryPlanes`. [H.265 V11 Annex I](https://www.itu.int/rec/T-REC-H.265-202601-I/en), [H.265.1 3D Main conformance table](https://www.itu.int/rec/dologin_pub.asp?id=T-REC-H.265.1-201810-I%21%21PDF-E&lang=e&type=items).

## SCC temporal MVP from IBC-only collocated pictures (2026-11-12)

The official H.265.1 `IBF_Disabled_A_MediaTek_2` and `IBF_Disabled_B_MediaTek_2` streams each contain 33 pictures (2 P and 31 B). In POC 16, the B slice uses POC 0 as its collocated picture. ## Constrained intra prediction

The PPS parser already exposed `constrained_intra_pred_flag`, but intra reference sampling did not use it. H.265 specifies that when this flag is 1, intra prediction may use residual data and reconstructed samples only from neighboring coding blocks coded with intra prediction modes. The decoder now tracks intra-coded 4×4 luma regions and treats inter-coded neighbors as unavailable during luma and subsampled chroma reference gathering.

`test/hevc-constrained-intra.test.ts` decodes all five pictures in the official 416×240 8-bit 4:2:0 `CIP_B_NEC_3` vector; the PPS flag is asserted and the full display-order Y/Cb/Cr output matches the published archive MD5 `1315714c7b3f3237b469259f66d9b7aa`. It also decodes the two-picture official `CIP_A_Panasonic_3` and `CIP_C_Panasonic_2` vectors, including their B pictures and CIP_C's three slices per picture; their display-order YUV MD5s match `4cbf601ba98d63f642defab5eaa12c8d` and `ed985932fef2aa8a74ded970070bdab2`. The CIP_B test additionally wraps its sequence as a synthetic HEIF `pred` graph and confirms that decoding its final item yields the same planes as direct sequence decoding. This is bounded evidence for these vectors, not a full H.265 conformance claim. macOS ImageIO selected a different master/thumbnail/pre-derived image than the declared primary in four gallery cases (C005, C040, bird_burst, rally_burst). Dimensions and metadata were compared; these differences are recorded rather than silently changing primary selection.

Apple HDR comparison in extended linear sRGB was not pixel-identical: a 1536×2048 iPhone image had RGB MAE approximately 0.0190 (max 0.2745); a 3024×4032 image at its full stored headroom 5.6187 had MAE approximately 0.0393 (max 0.2204). At requested headroom 4, the latter differs more because ImageIO reconstructed full source headroom. These comparisons include differing upsampling/color/gain-map choices. Default headroom now uses the full stored value. Physical HDR display behavior has not been validated.
